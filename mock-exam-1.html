Mock Exam 1 — 40 Questions with Rationale

This mock exam follows the official structure of the real ISTQB® CTFL v4.0 exam exactly: the chapter distribution, the cognitive levels, and the time all match the values in the official documents. None of the questions here copy real exam content; all are original questions written for exam preparation.

Exam rules (reminder)

Item Value
Number of questions 40 multiple-choice: 38 with one correct answer, and 2 “Select TWO” questions (16 and 32) with two correct answers among five options
Total points 40 (1 point per question)
Pass mark 26 points (65%)
Time 60 minutes (+25% only if your exam provider grants it; see How the CTFL Exam Works)

Cognitive distribution: K1 = 8, K2 = 24, K3 = 8. Chapter distribution: Chapter 1 → 8, Chapter 2 → 6, Chapter 3 → 4, Chapter 4 → 11, Chapter 5 → 9, Chapter 6 → 2.

How to use it. There are two ways. Timed mode: set a timer for 60 minutes (or 75 if your exam provider grants you the +25% extension), answer all 40 questions without looking anything up, and only then open the answer key in Part 2; this measures whether you are ready. Review mode: solve the questions chapter by chapter, untimed, and read the rationale in Part 3 after each; this strengthens your “why should I not have picked the distractor?” instinct. Whichever mode you choose, read the rationale even for the questions you answered correctly, because that is where the learning happens.

Part 1 — Questions

Do not look at the answer key in Part 2 until you have answered all 40 questions.

Chapter 1 — Fundamentals of Testing

Question 1. A product owner must decide whether a delayed feature can still go into the next release. She asks the testers for a summary of the defects found so far and the risks that remain. Which typical test objective does this request serve?

  • (a) Verifying that the test object complies with contractual and legal requirements
  • (b) Providing information to stakeholders to allow them to make informed decisions
  • (c) Validating whether the test object is complete and works as the stakeholders expect
  • (d) Ensuring the required coverage of the test object

Question 2. A flight-booking company does not tell a new developer about its rule that all departure times are stored in Coordinated Universal Time (UTC). The developer assumes that the times are local and writes code that stores them without conversion. A week after release, a passenger’s boarding reminder arrives an hour after the flight has left. Which statement classifies what happened correctly?

  • (a) The missing briefing is the error, and the code that stores local times is the failure
  • (b) The developer’s wrong assumption is the root cause, and the stored local times are the failure
  • (c) The developer’s wrong assumption is the error, and the late boarding reminder is the failure
  • (d) The code that stores local times is the root cause, and the missing briefing is the defect

Question 3. In one release, a reviewer spots two contradictory rules in a user story before any code is written, and the product owner corrects the story in ten minutes. In the next release, a similar contradiction is missed. It is built into the design and the code, copied into the test cases, and found only in production, where fixing it takes changes to the story, the design, the code, and the tests, plus an emergency patch. Which testing principle does this comparison illustrate best?

  • (a) Defects cluster together
  • (b) Testing shows the presence, not the absence, of defects
  • (c) The absence-of-defects fallacy
  • (d) Early testing saves time and money

Question 4. A tester takes the prioritised test conditions for a loyalty-points feature and turns them into test cases, identifying the coverage items each case must exercise. She also works out which data the cases will need and what the test environment must provide. Which test activity is she carrying out?

  • (a) Test analysis
  • (b) Test implementation
  • (c) Test planning
  • (d) Test design

Question 5. While deriving test conditions from a user story, a tester finds that two of its acceptance criteria contradict each other. The product owner cannot correct the story straight away, so the tester records the problem in a defect report. Which test activity produces this defect report as one of its work products?

  • (a) Test execution
  • (b) Test analysis
  • (c) Test design
  • (d) Test completion

Question 6. An auditor asks the test manager to show that every requirement in the release is covered by at least one executed test. Which property of the testware makes this question efficient to answer?

  • (a) Traceability between the test basis and the test work products
  • (b) The independence of the test team from the development team
  • (c) A high level of test automation in the regression suite
  • (d) Detailed entry criteria defined for each test level

Question 7. A department head asks an agile coach what her teams will gain by adopting the whole team approach. Which answer should the coach give?

  • (a) Each specialist can concentrate on their own tasks without taking part in other team activities
  • (b) A high level of test independence is achieved, which suits safety-critical products best
  • (c) The various skill sets within the team can be leveraged for the benefit of the project
  • (d) Responsibility for quality moves from the developers to a dedicated quality team

Question 8. A fintech company contracts an external test lab to test its mobile app. After two releases, the project manager lists four observations. Which observation describes a typical drawback of this high level of test independence?

  • (a) The lab’s testers challenged several assumptions in the specification, which delayed the sign-off of two user stories
  • (b) The lab’s testers found failures that the developers had missed, because they did not share the developers’ assumptions
  • (c) The lab’s testers learned about requirement changes late, because they were outside the team’s daily communication
  • (d) The developers continued to test their own components before handing builds to the lab

Part 3 — Answers, Explanations, and References

Show answers, explanations and references

Each question is explained option by option. The explanation names the strongest distractor, states the key takeaway, and gives the syllabus source. The Trap label after each answer says what kind of strongest distractor the question uses: a sibling concept (a neighbouring concept that shares features with the right one), a right idea in the wrong place (an accurate statement that belongs to another activity, level, or report), an overstated or reversed claim (a true statement stretched too far or turned round), or a calculation slip (a common mistake in applying a K3 technique).

Chapter 1 — Fundamentals of Testing

Question 1 — Correct answer: (b). Trap: sibling concept · LO 1.1.1 (K1). The product owner is a stakeholder facing a decision, and she asks testing for the facts she needs to make it: the defects found and the risks that remain. Providing information to stakeholders so that they can make informed decisions is one of the typical test objectives the syllabus lists, and it is exactly what this request serves. (a) compliance with contractual and legal requirements is a legitimate objective too, but nothing in the scenario mentions a contract, a law, or a regulator. (c) Validating that the test object works as the stakeholders expect is the strongest distractor because the scenario also involves a stakeholder, but validation checks the product against the stakeholders’ expectations; the product owner is not asking whether the feature meets her expectations, she is asking for input to a decision. (d) ensuring the required coverage concerns how thoroughly the test object is exercised, not how a decision is informed. Key takeaway: when a stakeholder asks testing for facts to support a go or no-go choice, the objective is providing information for informed decisions. Source: Syllabus 1.1.1. Review in this book: Typical test objectives (Section 1.1).

Question 2 — Correct answer: (c). Trap: sibling concept · LO 1.2.3 (K2). Read the chain in order. The root cause is the gap that made the mistake likely: the company never told the new developer about its UTC rule. The error is the person’s wrong action, the developer’s assumption that the times are local. The defect is what that error left in a work product, the code that stores times without conversion. The failure is what users experience at run time, the reminder that arrives after departure. Option (c) names the error and the failure correctly. (a) calls the missing briefing an error, but it is an organisational gap behind the error rather than a person’s wrong action; it also calls code a failure, whereas a flaw in code is a defect. (b) The developer’s wrong assumption is the root cause is the strongest distractor because the assumption does sit near the start of the chain, but it is the human action itself, the error; the root cause is the deeper reason the error happened, the missing briefing on the UTC rule. Its second half also labels a defect as a failure. (d) reverses two labels: the code is the defect, and the missing briefing is the root cause, not a defect, because it is not a flaw in any work product. Key takeaway: ask where each item lives, a gap in the organisation is a root cause, a person’s wrong action is an error, a flaw in a work product is a defect, and wrong behaviour at run time is a failure. Source: Syllabus 1.2.3. Review in this book: Errors, defects, failures, and root causes (Section 1.2).

Question 3 — Correct answer: (d). Trap: sibling concept · LO 1.3.1 (K2). The principle “early testing saves time and money” says that a defect removed early does not cause further defects in the work products derived from it, which lowers the cost of quality. The two releases show both sides: the contradiction caught in review cost ten minutes, while the one that slipped through spread into the design, the code, and the tests, and needed an emergency patch. (a) Defects cluster together is the strongest distractor because both contradictions sit in the same kind of work product, user stories, which can look like a cluster, but that principle explains where defects concentrate, not why the cost of a fix grows the later the defect is found. (b) is about what testing can prove, and nothing in the scenario turns on proving the absence of defects. (c) the absence-of-defects fallacy concerns a verified system that still fails its users’ needs, which is not the issue here. Key takeaway: when a scenario contrasts a cheap early fix with an expensive late fix of the same kind of defect, the principle is early testing. Source: Syllabus 1.3. Review in this book: The Seven Testing Principles (Section 1.3).

Question 4 — Correct answer: (d). Trap: right idea, wrong place · LO 1.4.1 (K2). Test design elaborates test conditions into test cases and other testware, often by identifying coverage items, and it also defines the test data requirements and designs the test environment. Each task in the scenario belongs there; test design answers the question “how to test?”. (a) test analysis comes one step earlier: it derives and prioritises the test conditions that this tester already has. (b) Test implementation is the strongest distractor because test data and the test environment both appear in the scenario, and implementation is where test data is created and the environment is built. However, the tester only works out which data is needed and what the environment must provide; creating the data and building the environment come later, in implementation. (c) test planning sets the objectives and the approach, not individual test cases. Key takeaway: defining and designing belong to test design, while creating and building belong to test implementation, so look at the verb before you choose. Source: Syllabus 1.4.1. Review in this book: Test activities (Section 1.4).

Question 5 — Correct answer: (b). Trap: right idea, wrong place · LO 1.4.3 (K2). The syllabus lists two kinds of work product for test analysis: prioritised test conditions, and defect reports about defects in the test basis when those defects are not fixed directly. The tester is deriving test conditions, which is test analysis, and the contradiction sits in the test basis, the user story. (a) Test execution is the strongest distractor because defect reports are the best-known output of test execution, but those reports describe failures observed when tests run; no test has run here, and the defect was found by reading the story. (c) test design produces test cases, test charters, coverage items, and test data and environment requirements. (d) test completion produces the test completion report, lessons learned, and change requests for unresolved defects. Key takeaway: write the ratio as a fraction and check the direction before you compute, development:test = 4:3 means test = development × 3/4. Source: Syllabus 5.1.4. Review in this book: Estimation techniques (Section 5.1).

Question 35 — Correct answer: (d). Trap: calculation slip · LO 5.1.5 (K3). In additional coverage prioritisation, the test case with the highest coverage runs first, and each next test case is the one that adds the most coverage not yet achieved. Step by step: TC1 exercises six statements, the most, so it runs first. After TC1, TC2 adds nothing (S1 to S5 are already covered), TC3 adds three statements (S7, S8, S9), and TC4 adds one (S10), so TC3 runs second. After TC3, TC4 still adds S10 while TC2 still adds nothing, so TC4 runs third and TC2 last. (a) TC1, TC2, TC3, TC4 is the strongest distractor because it applies plain coverage-based prioritisation, ordering by each test case’s own total (6, 5, 3, 2); the question names the additional variant, which counts only what is not yet covered. (b) applies the additional rule for the second slot but then falls back to the original order. (c) runs the test cases from the lowest coverage upwards, the reverse of any coverage-based strategy. Key takeaway: in additional coverage prioritisation, recompute what each remaining test case adds after every pick; a large test case that only repeats covered statements drops to the end. Source: Syllabus 5.1.5. Review in this book: Test case prioritisation (Section 5.1).

Question 36 — Correct answer: (a). Trap: right idea, wrong place · LO 5.3.2 (K2). Test progress reports support ongoing test control. The syllabus says they must provide enough information to modify the test schedule, resources, or test plan when testing deviates from the plan, and impediments with their workarounds are part of their typical content. A blocked environment halfway through the phase is exactly such a deviation. (b) lessons learned belong to the test completion report, written when the activity is over. (c) a progress report summarises the state of testing; it does not replace the individual defect reports, which still have to be raised. (d) The final evaluation of product quality against the exit criteria is the strongest distractor because a progress report does contain metrics and status, but the evaluation against the original plan and its exit criteria is the content of the test completion report, prepared at the end. Key takeaway: a progress report exists so that someone can steer while testing is still running, and a completion report evaluates and draws lessons after it has finished. Source: Syllabus 5.3.2. Review in this book: Test reports: progress and completion (Section 5.3).

Question 37 — Correct answer: (c). Trap: right idea, wrong place · LO 5.4.1 (K2). To support testing, configuration management ensures that all configuration items, including test items, are uniquely identified and version controlled, and that all identified documentation and software items are referenced unambiguously in testware. A report built on that discipline would name the exact build and suite version, and the auditor could check the claim. (a) More test automation is the strongest distractor because automated runs often produce detailed logs, but a log that does not record which build and which suite version ran has the same gap; the missing capability is identification and referencing, not automation. (b) exit criteria decide when testing may stop; they do not make a report name the versions it refers to. (d) defect reports describe individual anomalies, and a passed regression run may produce none, so they cannot document what was tested. Key takeaway: when evidence is rejected because no one can tell which version was tested, the answer is configuration management, with unique identification, version control, and unambiguous references in testware. Source: Syllabus 5.4. Review in this book: Configuration Management (Section 5.4).

Question 38 — Correct answer: (a). Trap: calculation slip · LO 5.5.1 (K3). The expected result is derived from the test basis and written as a concrete, observable value that can be compared with the actual result. The requirement awards one point for every full 10.00: an order of 527.40 contains 52 full units of 10.00 (52 × 10.00 = 520.00), and the remaining 7.40 is not a full unit. So the page should show 52 points. (b) 53 is the strongest distractor: it rounds 52.74 up, but “every full 10.00” counts complete units only. (c) is in the right spirit, but “the correct number” only restates the requirement; nobody can compare it with the actual result “0” without doing the calculation the tester skipped. (d) describes a fix, not the behaviour the system should show; a defect report states what should have happened and leaves the solution to whoever resolves the defect. Key takeaway: write the expected result as the exact value the test basis gives for these inputs. Source: Syllabus 5.5. Review in this book: Preparing a professional defect report (Section 5.5).

Question 39 — Correct answer: (b). Trap: sibling concept · LO 6.1.1 (K2). Tools that run automated test suites and measure how thoroughly the code has been exercised belong to the test execution and test coverage category. Running on every commit and gathering the results is part of the same job. (a) Test management tools is the strongest distractor because gathering and reporting results sounds like management, but test management tools manage the test process and testware, plans, progress, defects; the tool in the scenario runs the tests, and its reporting is a by-product of execution. (c) static testing tools examine work products without running them, whereas this tool runs the suites. (d) design and implementation tools help derive and prepare test cases; this tool runs tests that already exist. Key takeaway: classify a tool by its primary verb, if it runs the tests and measures coverage, it is a test execution and test coverage tool, whatever else it reports. Source: Syllabus 6.1.1. Question 40 — Correct answer: (d). Trap: right idea, wrong place · LO 6.2.1 (K1).
